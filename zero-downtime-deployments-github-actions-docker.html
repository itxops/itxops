Zero-Downtime Deployments with GitHub Actions and Docker

Scheduled maintenance windows and 15-second downtime gaps during git pushes are unacceptable for modern digital businesses. Here is how to achieve seamless, zero-downtime rolling cutovers with Docker and GitHub Actions.

ITXOps Engineering Desk
100% Remote Infrastructure • Operations Field Guide

Many development teams start with a simple deploy script: docker compose down && docker compose up -d.

The moment you run docker compose down, existing database connections are severed, in-flight HTTP requests fail with 502 Bad Gateway, and visitors see broken web pages for the 10 to 45 seconds it takes for your new container to initialize, run database migrations, and bind to port 3000.

Zero-downtime deployment ensures that the old application container continues answering live web traffic until the new container has fully initialized, passed automated health checks, and is ready for Nginx to switch upstream traffic smoothly.

1. The Architecture of Zero-Downtime Cutover

Rather than stopping the container, we implement an active Blue-Green port toggle pattern on the server:

  1. Suppose Container Blue is live on localhost:3001 behind Nginx.
  2. GitHub Actions builds the new image, transfers it, and starts Container Green on localhost:3002.
  3. A verification script polls http://localhost:3002/healthz until it returns HTTP 200 OK.
  4. Nginx points upstream traffic to localhost:3002 and executes nginx -s reload (which swaps traffic without terminating existing TCP sockets).
  5. Only after the cutover succeeds is the old Container Blue stopped.
  6. If Container Green fails its healthcheck within 60 seconds, it is automatically terminated and Container Blue remains untouched with zero impact to visitors.
Why Nginx Reload Drops Zero Connections
The command nginx -s reload instructs Nginx worker processes to finish serving current requests and exit gracefully while new workers immediately spawn to accept new traffic. No TCP connections are dropped.

2. Production GitHub Actions Workflow

Here is the complete .github/workflows/deploy.yml workflow configured with SSH key authentication and automated status reporting:

yaml • .github/workflows/deploy.yml 
name: Production Deployment

on:
  push:
    branches: [ main ]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Code
        uses: actions/checkout@v4

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Login to Container Registry
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and Push Docker Image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:latest,ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Deploy to Remote Linux Server via SSH
        uses: appleboy/ssh-action@v1.0.3
        with:
          host: ${{ secrets.SERVER_HOST }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SERVER_SSH_KEY }}
          script: |
            cd /opt/app
            ./scripts/deploy-cutover.sh ghcr.io/${{ github.repository }}:${{ github.sha }}

3. The Zero-Downtime Cutover Script

Save this script on your Linux server at /opt/app/scripts/deploy-cutover.sh:

bash • /opt/app/scripts/deploy-cutover.sh 
#!/bin/bash
set -e

NEW_IMAGE="$1"
CURRENT_PORT=$(cat /opt/app/.live_port 2>/dev/null || echo "3001")

if [ "$CURRENT_PORT" == "3001" ]; then
    NEW_PORT="3002"
    OLD_CONTAINER="app-blue"
    NEW_CONTAINER="app-green"
else
    NEW_PORT="3001"
    OLD_CONTAINER="app-green"
    NEW_CONTAINER="app-blue"
fi

echo "Pulling $NEW_IMAGE..."
docker pull "$NEW_IMAGE"

echo "Starting $NEW_CONTAINER on port $NEW_PORT..."
docker run -d \
    --name "$NEW_CONTAINER" \
    --restart unless-stopped \
    --env-file /opt/app/.env \
    -p "127.0.0.1:$NEW_PORT:3000" \
    "$NEW_IMAGE"

echo "Verifying healthcheck at http://127.0.0.1:$NEW_PORT/healthz..."
HEALTH_PASSED=false
for i in {1..30}; do
    if curl --fail --silent "http://127.0.0.1:$NEW_PORT/healthz" > /dev/null; then
        HEALTH_PASSED=true
        break
    fi
    echo "Waiting for container boot... ($i/30)"
    sleep 2
done

if [ "$HEALTH_PASSED" = false ]; then
    echo "ERROR: Health check failed on new container! Rolling back..."
    docker stop "$NEW_CONTAINER" || true
    docker rm "$NEW_CONTAINER" || true
    exit 1
fi

echo "Healthcheck passed! Switching Nginx traffic to port $NEW_PORT..."
sed -i "s/127.0.0.1:[0-9]*/127.0.0.1:$NEW_PORT/g" /etc/nginx/conf.d/upstream.conf
sudo nginx -s reload

echo "$NEW_PORT" > /opt/app/.live_port

echo "Stopping old container $OLD_CONTAINER gracefully..."
sleep 5
docker stop "$OLD_CONTAINER" || true
docker rm "$OLD_CONTAINER" || true

echo "SUCCESS: Zero-downtime deployment finished on port $NEW_PORT!"
Database Migration Strategy
If your release includes database schema migrations, ensure all migrations are backward-compatible (e.g. adding columns instead of renaming columns). Since both old and new containers run simultaneously for a few seconds, the old container must not crash on the updated schema!

4. Automated Rollback & Verification

Notice that if curl http://127.0.0.1:$NEW_PORT/healthz does not return HTTP 200 within 60 seconds (due to an uncaught crash, wrong environment variable, or database failure), the script exits with code 1. Because Nginx was never reloaded, your existing production traffic continues flowing uninterrupted through the previous container instance.
