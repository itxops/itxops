Fixing 502 Bad Gateway on Nginx Reverse Proxy: The Complete Field Guide

A 502 Bad Gateway indicates that Nginx, acting as a gateway or proxy, received an invalid or nonexistent response from the upstream application server. Here is how to diagnose and resolve it across Linux environments.

ITXOps Engineering Desk
100% Remote Infrastructure • Operations Field Guide

When a visitor requests a page and receives a bold 502 Bad Gateway error page from Nginx, the issue is almost never Nginx itself. Nginx is happily running, accepting TCP connections, and attempting to forward the request to your upstream backend (such as Node.js, Python Gunicorn, or PHP-FPM).

The 502 status code means: "I forwarded the request to your backend application, but the backend dropped the connection, refused the port, or returned garbage headers."

1. 502 Bad Gateway vs. 504 Gateway Timeout

Understanding the distinction between 502 and 504 saves hours of misguided debugging:

  • 502 Bad Gateway: Upstream actively rejected the connection (port closed, socket missing, or process immediately crashed). The failure happens within milliseconds.
  • 504 Gateway Timeout: Upstream accepted the connection, but took longer than proxy_read_timeout (typically 60s) to produce a response because of a hanging database query or infinite loop.
Always Check the Nginx Error Log First
Never guess. Open /var/log/nginx/error.log. It records the exact reason Nginx failed to reach the upstream.
bash • inspect error log 
$ sudo tail -n 25 /var/log/nginx/error.log

2. Step-by-Step Upstream Verification

Depending on your stack, run the corresponding diagnostic checks on the server:

Case A: Node.js / PM2 / Python Gunicorn Upstreams

Check if your backend process is actually listening on the expected port (e.g., 3000):

bash • node.js triage 
# Check PM2 process status
$ pm2 list
$ pm2 logs --lines 50

# Verify local listening port
$ sudo ss -tulpn | grep 3000

# Test localhost response directly without Nginx
$ curl -I http://127.0.0.1:3000

If curl returns Connection refused, PM2 has crashed or the Node.js application is caught in a boot loop.

Case B: PHP-FPM UNIX Sockets

In PHP-FPM setups, the error log usually says connect() to unix:/run/php/php8.2-fpm.sock failed (2: No such file or directory) or (13: Permission denied).

bash • php-fpm triage 
# Check PHP-FPM service status
$ sudo systemctl status php8.2-fpm

# Verify socket exists and permissions match www-data
$ ls -la /run/php/php8.2-fpm.sock
srw-rw----+ 1 www-data www-data 0 Oct 23 06:00 /run/php/php8.2-fpm.sock

# Restart PHP-FPM if locked
$ sudo systemctl restart php8.2-fpm
SELinux or AppArmor Permissions Trap
On CentOS/RHEL or hardened Ubuntu, SELinux policies often block Nginx from connecting to network ports or sockets. Check: sudo getsebool httpd_can_network_connect. If off, enable it with sudo setsebool -P httpd_can_network_connect 1.

3. Fixing Buffer Overflow 502 Errors

If your application returns very large response headers (common with OAuth JWT tokens, extensive Set-Cookie headers, or complex CMS frameworks), Nginx will drop the connection and report: upstream sent too big header while reading response header from upstream.

Add these buffer tuning directives inside your server or location block:

nginx • buffer tuning 
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;

    # Buffer adjustments for large headers & cookies
    proxy_buffer_size          128k;
    proxy_buffers              4 256k;
    proxy_busy_buffers_size    256k;

    # Standard proxy headers
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}

4. Hardened Production Nginx Reverse Proxy Template

Here is our benchmark configuration for production Node.js and backend proxies with health check fallback:

nginx • /etc/nginx/sites-available/app 
upstream backend_cluster {
    server 127.0.0.1:3000 max_fails=3 fail_timeout=10s;
    keepalive 32;
}

server {
    listen 80;
    server_name api.example.com;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name api.example.com;

    ssl_certificate /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    location / {
        proxy_pass http://backend_cluster;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_connect_timeout 5s;
        proxy_read_timeout    60s;
        proxy_send_timeout    60s;

        proxy_buffer_size          128k;
        proxy_buffers              4 256k;
    }
}
Always Test Before Reloading
Always verify syntax before executing reload: sudo nginx -t. Only when you see syntax is ok and test is successful should you run sudo systemctl reload nginx.
