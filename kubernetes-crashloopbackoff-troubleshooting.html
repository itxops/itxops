How to Troubleshoot Kubernetes CrashLoopBackOff Step-by-Step

One of the most frequent alerts in containerized production environments. Here is the exact diagnostic workflow to identify exit codes, isolate memory limits, and stop the crash loop permanently.

ITX
ITXOps Engineering Desk
100% Remote Infrastructure • Operations Field Guide

When deploying microservices to Kubernetes, few statuses cause more immediate confusion than CrashLoopBackOff. The word CrashLoopBackOff sounds severe, but understanding its lifecycle demystifies the error: it is not an error generated by your code — it is an informational status emitted by the kubelet signaling that your container started, exited unexpectedly, and Kubernetes is waiting before trying to start it again.

1. What CrashLoopBackOff Actually Means

The lifecycle follows a simple mathematical progression:

  1. The container runs its entrypoint process.
  2. The process terminates with a non-zero exit code (or is terminated by the Linux kernel).
  3. The kubelet restarts the container immediately.
  4. If the crash recurs, Kubernetes applies an exponential back-off delay: 10s, 20s, 40s, 80s, up to a maximum of 300 seconds (5 minutes).
Important Distinction
The container image itself is downloaded and valid. If the image couldn't be pulled, the status would be ImagePullBackOff. The container is crashing after initialization.

2. The 4 Root Causes and Their Exit Codes

Containers always exit with an exit code. Inspecting the exit code narrows down the root cause in 90% of outages:

  • Exit Code 137 (SIGKILL / OOMKilled): The container exceeded its memory limit defined under resources.limits.memory, or the host node ran out of RAM and the Linux kernel Out-Of-Memory killer terminated the process.
  • Exit Code 1 (Application Error): A fatal uncaught exception occurred in runtime (e.g. Node.js uncaughtException, Python SyntaxError, or Go panic).
  • Exit Code 139 (SIGSEGV): A memory segmentation fault occurred in a compiled binary or shared C library.
  • Exit Code 0: The process completed its task and cleanly exited (often happens when running a script that is not an ongoing server daemon).
OOMKilled Trap
If you see exit code 137, your application might not be leaking memory — your resources.limits.memory might simply be configured lower than the JVM or Node.js heap startup requirement.

3. 4 Essential kubectl Triage Commands

Run these four commands in sequence from your terminal to pinpoint the crash reason:

Step 1: Check Pod Status & Recent Restarts

bash • step 1 
$ kubectl get pods -n production -l app=api-service
NAME                           READY   STATUS             RESTARTS       AGE
api-service-59695d7f6c-wz8pl   0/1     CrashLoopBackOff   5 (2m14s ago)  8m

Step 2: Inspect Exit Code & Last State via Describe

Look specifically at the Last State block and the Events: table at the bottom of the output:

bash • step 2 
$ kubectl describe pod api-service-59695d7f6c-wz8pl -n production

In the output, examine this crucial section:

yaml • describe output excerpt 
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Mon, 23 Oct 2026 06:12:45 +0000
      Finished:     Mon, 23 Oct 2026 06:13:02 +0000

Step 3: Retrieve the Previous Container Instance Crash Logs

If you run regular kubectl logs, you will often see an empty output because the container just restarted and hasn't written any stdout yet. The --previous flag tells Kubernetes to retrieve logs from the crashed container instance:

bash • step 3 
$ kubectl logs api-service-59695d7f6c-wz8pl -n production --previous

Step 4: Debug Interactively with an Ephemeral Container or Sleep Override

If the container crashes before you can inspect it, temporarily override its entrypoint in staging to keep the container awake:

yaml • deployment override 
spec:
  containers:
  - name: api-service
    image: registry.example.com/api:v2.4.1
    command: ["/bin/sh", "-c", "sleep 3600"]

4. Real-World Production Fix Example

In a recent client case, an automated payment gateway crashed every 45 seconds. Running kubectl describe pod revealed:

  • Exit Code: 137 (OOMKilled)
  • Memory Limit: 256Mi
  • Startup RSS: 310Mi during initial cache warming.

Here was the fixed resource block in the Kubernetes Deployment manifest:

yaml • deployment.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-service
  namespace: production
spec:
  replicas: 3
  template:
    spec:
      containers:
      - name: api-service
        image: registry.example.com/api:v2.4.2
        resources:
          requests:
            memory: "384Mi"
            cpu: "250m"
          limits:
            memory: "768Mi"
            cpu: "1000m"
        livenessProbe:
          httpGet:
            path: /healthz
            port: 8080
          initialDelaySeconds: 30
          periodSeconds: 10
          failureThreshold: 3
Pro Tip: Liveness Probe Timing
Always configure initialDelaySeconds appropriately. If your app takes 20 seconds to connect to Redis and PostgreSQL on boot, a probe that tests after 5 seconds will repeatedly trigger SIGKILL and force a CrashLoopBackOff!

5. Production Prevention Checklist

  • Always define both requests and limits: Never omit memory limits, or a single runaway process can crash neighboring pods on the node.
  • Add Graceful Shutdown Handlers: Trap SIGTERM signals so in-flight requests finish cleanly within terminationGracePeriodSeconds: 30.
  • Log to stdout/stderr: Do not write logs exclusively to file paths inside the ephemeral container disk.
  • Set up Alertmanager rules: Trigger Slack/email warnings whenever any pod restart count exceeds 3 in a 10-minute window.
